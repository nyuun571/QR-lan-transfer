# 運用手順書 (Runbook) — QRDrop v0.1.0

> 各手順は 2026-07-12 に実際に実行して検証済み(ローカルアプリのため本番影響なし)。

## システム概要

- 構成: [design-doc.md](../design/design-doc.md) 参照。Go 製の単一 exe。PC 上で HTTP サーバを起動し、LAN 内のスマホがブラウザ(QR 読取)で接続する。外部サービス・常駐サービスなし(使うときだけ起動する対話型アプリ)
- 稼働環境: ユーザー PC(Windows 11)上の `qrdrop.exe`。管理ページ `http://127.0.0.1:<port>/admin`(ループバック限定)、既定ポート 8080(使用中なら自動フォールバック)
- 連絡先: 障害・不具合はユーザー本人が本セッション(Claude Code)へ報告 → 7-2/7-3 のフローで対応

## 起動 / 停止 / 再起動

```
# 起動(検証日: 2026-07-12。ビルド済み exe がある場合)
cd 04-qr-lan-transfer\qrdrop
.\qrdrop.exe
#   → 管理ページが自動で開く。QR をスマホで読み取る
#   → オプション: -port <n> / -dir <受信フォルダ> / -ttl <分> / -no-browser

# ビルドから行う場合(検証日: 2026-07-12)
set GOTOOLCHAIN=go1.26.5   # 必須。既定 1.26.1 には stdlib 脆弱性あり(レビュー指摘 #1)
go build ./cmd/qrdrop

# 停止(検証日: 2026-07-12)
#   起動したコンソールで Ctrl+C(残プロセスは taskkill /IM qrdrop.exe で強制終了可)

# 再起動 = 停止 → 起動(セッショントークンは再発行される。スマホは QR 再読取が必要)
```

## 監視

- ヘルスチェック方法: `curl -s -o NUL -w "%{http_code}" http://127.0.0.1:<port>/admin` が `200` を返せば正常(検証日: 2026-07-12)
- ログの場所と見方: `%APPDATA%\QRDrop\logs\qrdrop-YYYYMMDD.log`(日付別・接続元 IP/操作/ファイル名/結果のみ。本文は非記録 = NFR-004)
  - 正常操作: `op=upload|share|download ... result=ok`
  - 遮断: `deny remote=... reason=no-token-path|invalid-token|...`(不正アクセス試行の痕跡はここに残る)
- 正常性の判断基準: 管理ページ 200 + 転送操作の `result=ok`。`deny` の多発は LAN 内の意図しないアクセス試行を疑う(セッション失効ボタンで即時遮断可 = REQ-005)

## よくある問題と対処

| 事象 | 原因 | 対処 | 追記日 |
|------|------|------|--------|
| スマホの進捗バー表示が未検証(TC-013) | 開発環境に実機なし(Could 要件) | 初回利用時に目視確認。問題があれば変更要求として受付 | 2026-07-12 |
| 実機ブラウザ(iOS Safari / Android Chrome)固有の挙動差 | 実機一気通貫は HTTP+QR デコードで代替検証済み | 発生したら事象・機種・ブラウザを記録して報告 | 2026-07-12 |
| 同時同名アップロードで稀に 500(レビュー Minor #2) | 連番採番の競合 | 再送すれば成功する。頻発時は変更要求 | 2026-07-12 |
| スマホから接続できない | ファイアウォールで「プライベート」未許可 / PC とスマホが別ネットワーク(ゲスト Wi-Fi 等)/ セッション失効(TTL 30 分) | FW 許可を確認 → 同一 SSID を確認 → 管理ページで QR 再発行 | 2026-07-12 |
| 起動時「LAN に接続されていません」エラー | LAN 未接続(REQ-001 異常系) | ネットワーク接続後に再起動 | 2026-07-12 |
| ポート 8080 が使用中 | 他アプリと競合 | 自動フォールバックあり。固定したい場合は `-port` 指定 | 2026-07-12 |
