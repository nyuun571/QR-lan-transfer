# ADR-001: アーキテクチャに「Go 製ローカル HTTP サーバ + ブラウザ UI」を採用

- **日付**: 2026-07-09
- **状態**: 提案(G2 承認待ち)
- **決定者**: Architect(Claude Code)

## 文脈 (Context)

「QR コードで接続し、同一ネットワーク内のみでスマホ⇔PC のデータ転送を行う」
(REQ-001〜004)を実現する基本方式を決める。スマホ側はアプリ不要(DEC-003)が前提。

## 検討した選択肢

### 案A: PC 上のローカル HTTP サーバ(Go 単一バイナリ)+ スマホはブラウザ — 採用

- 利点: 転送はすべて LAN 内で完結(REQ-004 と本質的に整合)、スマホ側インストール不要、Go は単一 exe 配布・依存ゼロ・標準ライブラリで multipart/SSE まで賄える
- 欠点: PC 側にファイアウォール許可が必要。LAN 内は平文 HTTP(→ ADR-002)

### 案B: クラウド中継(WebSocket リレーサーバ経由)— 却下

- 利点: NAT・AP アイソレーションの影響を受けない、LAN 外からも使える
- 欠点: データが外部サーバを経由する
- 却下理由: 「同一ネットワーク内でしか行われない」という Must 要求(REQ-004)に真っ向から反する

### 案C: WebRTC DataChannel(P2P)+ QR でシグナリング情報交換 — 却下

- 利点: 転送自体は P2P、DTLS で暗号化される
- 欠点: シグナリングに何らかの中継(または QR への SDP 埋め込みという不安定な手法)が必要、STUN 参照で外部通信が発生しうる、実装複雑度が高い
- 却下理由: 複雑さに見合う利点がない(LAN 内なら HTTP 直結で十分高速)。外部 STUN への通信は REQ-004 の趣旨に反する

### 案D: 既存 OSS(LocalSend / Snapdrop 等)の利用 — 却下

- 利点: 実装不要
- 欠点: LocalSend は両端アプリ必須(DEC-003 に反する)、Snapdrop 系は PWA 配信サーバに依存
- 却下理由: 「QR を読むだけ・アプリ不要・完全 LAN 内」の3点を同時に満たす既存物が見当たらないことが本プロジェクトの動機

## 決定 (Decision)

案A を採用する。要求の中核である「同一ネットワーク限定」を構造そのもの
(LAN 内 HTTP 直結・外部要素ゼロ)で満たせる唯一の案のため。

## 影響 (Consequences)

- 初回起動時に Windows ファイアウォールの受信許可が必要(セットアップ手順に記載)
- AP アイソレーション有効なルーターでは動作しない(仕様として README に明記)
- 費用: なし(依存ライブラリは go-qrcode のみ、MIT ライセンス)
